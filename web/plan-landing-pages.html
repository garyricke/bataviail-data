0The reframe: design themes, not pages

Every bespoke reference page (River West, Coffee & Sawdust, Walder, Chuck's, Hager) is the same recipe underneath. The design lives in the theme, not the page.

/* what every "pro" page actually is */ :root { unique palette (5–8 colors) + unique font pairing (display · head · body) } → hero with real photography + eyebrow + big display headline → narrative sections in a deliberate order (story → services → proof → CTA)

River West is "iron / gold / teal, Bebas Neue, gritty gym." Coffee & Sawdust is "espresso / sawdust / walnut, Alfa Slab One, warm maker." These aren't four unique websites — they're four theme archetypes. Once a theme exists, pouring a different business's data, palette, and photos through it produces another bespoke-looking page for free.

The whole plan in one line

Build ~8 excellent themes, let data + the agent swarm fill them. Thousands of pages that each look designed — without thousands of design projects.

1One quality ladder every entity climbs

Your two questions — "personas feel samey" and "how do we host pro pages" — are the same ladder at two rungs. This ladder is the business model: each rung maps to a roadmap phase.

2Problem 1 — make personas distinct (the quick win)

Today each persona is {color, categories} and swaps a single accent — same navy background, same font everywhere. Give each persona a full theme token set (palette + font pairing + hero style), and they stop feeling samey. This is the idea you originally proposed, actually realized.

How it stays behind the existing seam

Extend each persona in personas.js with a theme block, then one applyPersonaTheme(key) sets CSS vars and injects the Google fonts — reusing the injectFonts() you already have for entities. No structural rewrite; the rankForPersona / config-as-data seam is untouched. ~half a day, and it produces the palette + font vocabulary the entity themes reuse.

{ key:"socialite", label:"Downtown Socialite", /* …categories… */ theme:{ bg:"#140e1f", surface:"#1e1630", ink:"#f3e9ff", accent:"#c9a24a", accent2:"#8b5cf6", fontDisplay:"Fraunces", fontBody:"Inter", heroStyle:"editorial" } }

3Problem 2 — the theme engine (the big prize)

Three pieces, all consistent with "thin frontend over views + agent swarm." Turn entity.html from one fixed layout into a composition engine.

1 · Composition engine

A library of section components — hero variants, story block, services grid, gallery, testimonial, events, stats band, map/CTA, lead form. A theme = palette + font pairing + which sections, in what order + hero variant. Themes are data (themes.js now → a themes table later), exactly like personas.js.

2 · Agent-authored content

What makes the samples read as "pro" isn't just CSS — it's real storytelling copy, curated photography, a chosen palette. That's the redesign you did by hand for Hager. The swarm already writes summaries + pulls media; extend it to write long-form section copy, crop a hero, and propose a per-entity palette. Fixed excellent design + agent-filled richness = bespoke feel at scale.

3 · Category → theme mapping

Each entity gets a theme key, auto-assigned by category (gym → "iron," maker/retail → "warm," nonprofit → "civic"), and overridable when claimed. One entity.html reads the entity + its theme and assembles the page. Zero per-entity files.

4Rendering & scale

Start client-side (fits the no-build frontend), add prerender when SEO on thousands of pages actually matters — reusing infrastructure you already built.

Now — client-side themes

  • Render Tiers 1–2 from entity_full in the browser
  • Matches the no-build ethos; always fresh; free for all entities
  • Add entities.slug → pretty URLs like /o/coffee-and-sawdust

Later — static prerender (when SEO demands)

  • A generator feeds the same views into the themes → static HTML per page
  • Triggered by the same repository_dispatch you built for photo uploads
  • A build step is off-brand for the frontend, but fits the Python/agent + CI half you already run

Tier 3 bespoke pages are stored as a section-spec JSON (or full custom HTML for true one-offs) in an entity_pages table — versioned, with a published flag — so a Pro page is data too, editable through the future claim flow.

5Data model changes

Small, additive, and reused everywhere. One expansion of brand fixes both the persona-theming gap and the entity-theme gap.

entities.slugnew
Pretty, stable URL segment (/o/<slug>) instead of a raw UUID. SEO + shareable.
entities.themenew
Theme key, auto-assigned by category, overridable on claim. Drives which template renders.
brand.{bg,surface,ink,font_body}extend
Today brand has primary / accent / font_heading. Themes need background, surface, ink, and a body font to theme fully — same gap as the personas.
entity_pagesnew
entity_id · tier · theme_key · layout_json · long_copy · custom_html · published · version. Home for Tier 3 bespoke pages, as data.
themeslater
Starts as web/themes.js (the seam), graduates to a table when theme definitions want to live in the DB.

6Honest limits

So we don't paint into a corner or over-promise.

  • Bespoke ≠ scalable; themes = scalable. Don't promise thousands of hand-built pages — promise thousands of themed pages plus hundreds of bespoke Pro ones.
  • Client rendering hurts SEO at volume. That's the trigger for the prerender step — not a day-one problem.
  • brand needs more tokens before themes can theme fully. Expand it once, reuse it in personas and entity themes alike.
  • Theme quality is a ceiling. Eight great themes beat forty mediocre ones. Grow the library deliberately, seeded from real Batavia businesses.
