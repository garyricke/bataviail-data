BataviaIL Data — How It Works

A data-first community platform for Batavia, IL: a Supabase source-of-truth grown by an AI agent swarm, with a public directory and a mobile photo-capture app. This page explains every piece.

Overview

The core product is the data. Instead of building a website and stuffing data into it, we built a structured database first, then grew it automatically and put thin interfaces on top.

Every Batavia organization is an entity in a Postgres database. AI agents visit each org's website, read it, and extract structured facts — what it does, its services, hours, events, social links, contacts, and even its brand colors and fonts. A second track lets people capture real photos on location that get styled to a consistent professional look. Two front-ends read this data live: a public directory and a mobile capture app.

Why data-first? Because the data outlives any one interface. The same database can power a directory today, a newsletter tomorrow, and a personalized app later — without re-collecting anything.

Architecture

Three layers, one source of truth:

Agent swarmPython · scout + Claude
→
Supabase Postgressource of truth + Storage
←
Static front-endsdirectory + capture PWA
  • Supabase Postgres is the single source of truth. All reads and writes go through it. Row-Level Security (RLS) governs who sees what.
  • The agent swarm (Python scripts) writes into the database — scraping, enriching, and image processing — using the secret key, which bypasses RLS.
  • The front-ends are plain static HTML (no build step). They read through the public anon key, which RLS limits to read-only public views. Hosted on Netlify.
  • Supabase Storage holds the hero images (public bucket) and raw photo uploads.
Nothing sensitive ships to the browser. The page carries only the publishable key, and RLS makes it read-only and blind to internal tables (like the raw FOIA quarantine).

Data model

The database is organized around a clean entity with satellite tables for each kind of fact, plus a quarantine zone for unverified inputs.

The browser never queries these tables directly. It reads two views: entities_summary (the grid) and entity_full (everything for one card — joins in services, events, hours, contacts, social, categories, address, brand, hero).

The agent pipeline

For each entity, three steps run — all throttled, resumable, and cost-capped:

① Scoutfetch site, extract signals
→
② EnrichClaude Sonnet → structured
→
③ Applywrite + audit
  • Scout (agents/scout.py) fetches the homepage (and an events page if it finds one), extracts contacts/social via regex, and mines brand signals — theme-color, fonts, CSS color variables, and color frequency from the page and its stylesheet. Raw HTML is cached for change detection.
  • Enrich (agents/enrich.py) sends the scraped text to claude-sonnet-4-6 via strict tool use, getting back validated JSON: a summary, services, hours, dated events, and a synthesized brand palette + fonts. It only keeps facts the page actually supports — it won't invent hours or events.
  • Apply (agents/db.py) writes directly to the live tables (data-build phase, no manual review gate) and records an entity_changelog row so every change is traceable and reversible.

The runner agents/run_all.py drives this across all entities with a concurrency cap, a hard cost cap, failure isolation, and resume-on-restart.

Daily events refresher

Events expire, so a dedicated agent (agents/refresh_events.py) keeps them current — it runs automatically every day on GitHub Actions (.github/workflows/refresh-events.yml, no laptop needed). To stay cheap it leans entirely on change detection:

  • It re-scouts every site (HTTP + content-hash compare, and no paid search) — that part is free.
  • It spends a cheap claude-haiku-4-5 call only when a site's events/calendar page actually changed, then writes only the events (an idempotent upsert) — never touching summaries, brand, or deep-enrichment state. Typical cost is a few cents a day.
  • Past events need no cleanup: the entity_full view only returns starts_at >= now(), so finished events drop off the site on their own.

Hero images

Two ways an entity gets a hero photo, both labeled on the card:

KindHow
AI EnhancedThe org's own site photo, run through an image model to a polished look.
AI GeneratedNo usable photo found → a representative editorial image is generated.
Community PhotoA real on-location photo (from the capture app), styled to the consistent "house look."

The house look is the key to consistency: every image runs through one identical enhancement recipe (a locked prompt), so photos from any contributor share a single aesthetic. Generated by OpenAI gpt-image-2; stored in Supabase Storage. Runner: agents/heroes.py.

The capture app

A mobile web app (PWA) for shooting business photos on location:

📱 capture.htmlpick place · photo · GPS
→
Storage + queuephoto_uploads
→
process_uploads.pystyle · geocode · publish
  • Passcode-gated. You search/pick a business (or add a new place), take a photo or choose one from your library, and it grabs GPS.
  • The photo uploads to Supabase Storage and a photo_uploads row is queued — instant, so you can keep shooting.
  • The worker (agents/process_uploads.py) processes the queue: styles each photo to the house look, stores the hero, reverse-geocodes the GPS to a street address, and sets it as the entity's hero.
  • The worker runs automatically on GitHub Actions (workflow .github/workflows/process-uploads.yml) on a 5-minute schedule — no laptop needed. So a shot is typically styled and live within a few minutes of upload.
Trigger it manually (instead of waiting for the 5-minute cron):
  • GitHub UI: repo → Actions → Process photo-capture queue → Run workflow.
  • Command line: gh workflow run "Process photo-capture queue" --ref main
Either runs the same job that processes any pending uploads. You can still run it locally as a backup with .venv/bin/python -m agents.process_uploads --loop.

Frontend & security

  • Directory (index.html): reads entity_full live via the anon key. Each card is styled in that org's own brand colors and fonts, shows its hero, address, services, events, hours, social, and contacts. Community photos are featured first.
  • Security: the anon (publishable) key is RLS-gated to read-only on the public views only. The secret key (server-side, never shipped) bypasses RLS for the agents. The FOIA quarantine and ops tables are invisible to the browser.
  • Both front-ends are static — no build step, deploy by pushing to Git → Netlify.

How to run it

# one-time setup
cp .env.example .env                      # fill Supabase + API keys
python -m venv .venv && .venv/bin/pip install -r loaders/requirements.txt
.venv/bin/python loaders/apply_migrations.py   # build the schema
.venv/bin/python loaders/load_chamber.py       # load 521 chamber orgs
.venv/bin/python loaders/load_foia_quarantine.py

# grow the data (live)
DRY_RUN=0 .venv/bin/python -m agents.run_all --refresh   # enrich everything
DRY_RUN=0 .venv/bin/python -m agents.heroes              # hero images

# capture app — normally runs itself on GitHub Actions every 5 min.
# Trigger a run now (instead of waiting for the cron):
gh workflow run "Process photo-capture queue" --ref main
# …or process locally as a backup:
DRY_RUN=0 .venv/bin/python -m agents.process_uploads --loop   # process photos as they're shot

# events freshness — runs itself daily on GitHub Actions.
gh workflow run "Refresh events" --ref main                   # trigger a crawl now
DRY_RUN=0 .venv/bin/python -m agents.refresh_events           # …or run it locally
